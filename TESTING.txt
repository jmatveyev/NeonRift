NEON RIFT 1.3 - RELEASE VALIDATION
==================================

The Neon Rift 1.3 release is assembled and validated in GitHub Actions using
headless Chromium with real keyboard events, Chromium emulated touchscreen input,
network interception for managed Supabase client tests, and strict source/build
guards.

======================
Startup smoke: PASS
Legacy mobile/desktop regression suite: 147 / 147 assertions PASS

The production launch files also pass JavaScript syntax, save-compatibility,
client-credential, and byte-identity validation before the release is committed.

STARTUP / INITIALIZATION REGRESSION
===================================
A separate startup smoke test forces the QA hook on in an actual browser and
fails on any uncaught page exception. This test exposed and fixed an initialization
ordering defect inherited from the earlier career build: the old generated page
could call career-home synchronization before the career object finished
initializing. Neon Rift 1.3 defers that synchronization until initialization is
complete. The final startup smoke passes.

BUILD AND SAVE-COMPATIBILITY GATES
==================================
The release workflow rebuilds from an approved baseline rather than editing an
unknown generated file. It then verifies:

- index.html and neon-rift.html are byte-identical.
- All inline JavaScript parses successfully.
- The original `neon-rift-save-v1` key remains present.
- The career `neon-rift-career-v1` key remains present.
- 1.3 player identity uses `neon-rift-player-v1`.
- 1.3 checkpoint resume uses `neon-rift-checkpoint-v1`.
- Music remains enabled by default for new players.
- Existing localStorage save paths remain intact.
- The browser uses only the public `sb_publishable_...` key.
- No `sb_secret_...` or service-role credential is shipped to the browser.

BACKEND SECURITY VALIDATION
===========================
The Supabase 1.3 migration and Edge Function were separately validated against the
production project:

- RLS is enabled on player/session/telemetry/rate-limit tables.
- Anonymous/authenticated roles have no access to those backend-only tables.
- Anonymous access to `runs` is SELECT only.
- Direct anonymous leaderboard INSERT/UPDATE/DELETE is revoked.
- Run writes go through the `game-session` Edge Function.
- The function validates the public application key, session token hash, active
  session, run-shape constraints, elapsed time sanity, duplicate run IDs, broad
  score bounds, and request rate limits.
- Daily runs are restricted to the nine-sector daily objective.
- The deployed Edge Function is version 2 and stores only a coarse platform label,
  not the raw browser user-agent string.
- Supabase Security Advisor reports zero findings after the 1.3 migrations.

LIMITATIONS
===========
This is strong automated release validation, not a claim of universal bug-free
operation. The final release has not been manually certified on physical iPhone
or Android hardware, Safari/WebKit, every browser-management policy, or every
possible accessibility configuration.

The leaderboard is hardened against casual direct-database score fabrication but
the game remains client-authoritative. It is not a fully server-simulated or
cryptographically provable competitive environment.
